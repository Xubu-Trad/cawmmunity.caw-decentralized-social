# Minimal committee G1 composition — 2026-11-07

Research only. Parent: `382b5602c3de32c928fcc94411ea3f202711b6c3`.

## FACT

The isolated `experiments/bls-g1/committee.mjs` now validates the retained minimal committee's 32 individual G1 public keys and supplied aggregate public key, then checks that adding the listed member points equals the supplied aggregate. Each key goes through the [canonical G1 adapter](BLS_G1_VALIDATION_20261107.md): compressed encoding equality, curve/subgroup membership and nonidentity. The pinned library performs point arithmetic; no new curve arithmetic is implemented here.

The fixed standalone interface admits exactly `pubkeys` and `aggregate_pubkey`, exactly 32 members and lowercase 48-byte hex encodings, within an 8 KiB JSON bound. It is not a general/mainnet committee interface. Canonical identity keys or identity aggregate are rejected by this research profile; no claim is made that this covers every conceivable consensus-valid aggregate edge case.

The composed interface first runs the unchanged V3 profile/metadata/bootstrap structural verifier, then checks the same parsed committee's keys and sum. The original verifier's `publicKeysValidated` and `aggregatePubkeyValidated` flags remain false. Only the new research result sets them true after checking the keys. No root dependency, old source module, default test command, application or recovery-adoption behavior changes.

The retained binding stays 6,690 bytes, SHA-256 `96f107e5a94bd2a9bfa47f84ff257cbd18995ae8947440cac91804823236c6f8`. It contains the official retained fixture's 32 keys and aggregate, so the expected aggregate is external retained evidence, not generated by this new checker. The original fixture decode was not rerun. Its [historical checksum correction](BOOTSTRAP_BINDING_PROVENANCE_CORRECTION_20261107.md) and original inconsistent evidence remain untouched.

The [pinned Altair specification](https://github.com/ethereum/consensus-specs/blob/204fb4a19774eabb7a2e91505365deed6b8afef8/specs/altair/beacon-chain.md#get_next_sync_committee) permits repeated validator indices/pubkeys and aggregates the resulting list. The source identity and inspected sections are retained in `spec-source.json`. The checker therefore counts multiplicity and does not deduplicate. A synthetic repeated-key case compares repeated addition to scalar multiplication as a local control, not an independent cryptographic implementation.

## INFERENCE

Point addition does not bind order: exchanging two members leaves the aggregate relation true but the original ordered SSZ inclusion proof rejects. The experiment retains that contrast. A valid replacement member also remains a valid point yet fails the unchanged aggregate relation. Neither algebraic relation alone supplies chain authority.

The composed result establishes a bounded relationship among the retained metadata, selected root, ordered structural inclusion, valid individual keys and supplied aggregate. It does not establish independently authenticated committee membership or trust anchor, proof of possession, a signature, G2 validity, signing domain, fork schedule, consensus, freshness, finality or update acceptance. `blsValidated` remains false as an overall bootstrap-validation flag; the narrower key and aggregate-property flags are explicit. All authentication and acceptance flags remain false.

The pinned library's earlier raw decoder mismatch is not erased by these passing checks. No claim of complete BLS conformance, independent source-build reproduction, current security clearance or production suitability follows. Full suite, build, EVM, live acquisition and CI were not run; hosted CI remains deferred.
