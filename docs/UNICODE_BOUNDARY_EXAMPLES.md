# Unicode boundary examples for the C-004 review

This is comparison evidence for
[C-004: Review what the 420-character limit counts](https://github.com/Xubu-Trad/cawmmunity.caw-decentralized-social/issues/8).
It supplies the human-readable table requested in
[Issue #9](https://github.com/Xubu-Trad/cawmmunity.caw-decentralized-social/issues/9).

This guide does not decide the character rule, does not change any
contract, and does not change any validation logic. The current demo
rule is provisional: it counts Unicode scalar values (code points),
not bytes and not grapheme clusters. A grapheme count may differ from
the scalar count for the same text, as the tables below show.

## How the three counts are defined here

- **UTF-8 bytes**: `new TextEncoder().encode(text).length`.
- **Unicode scalars**: `countCharacters(text)` in `public/model.mjs`.
  It counts Unicode code points (`Array.from(text).length`) and rejects
  unpaired surrogates with `INVALID_UNICODE`. It does not normalize
  the text: composed and decomposed forms keep different counts.
- **Graphemes**: `Intl.Segmenter` with granularity `grapheme`, using
  only the existing Node runtime. No dependency is added for counting.
  Grapheme segmentation is a display-oriented grouping, not a
  normative protocol rule, and its results can depend on the runtime's
  segmentation data. Grapheme counts are shown only to make the
  difference from scalar counts visible.

The example file `docs/unicode-boundary-examples.txt` contains the
Table 1 examples as actual UTF-8 text, each preceded by a label line
(`ASCII`, `composed`, `decomposed`, `emoji`, `ZWJ`, `flag`, `RTL`,
`newline`, `URL`), in the same order as Table 1. The newline example
spans the two lines between `[newline]` and `[/newline]`; its escaped
form is `a\nb`. Boundary examples are not pasted into either file;
they are generated by the command in the verification section.

## Table 1: small examples

Escaped forms are shown so invisible characters can be inspected.
All text below is synthetic.

| Example | Escaped form | UTF-8 bytes | Unicode scalars | Graphemes | Note |
| --- | --- | --- | --- | --- | --- |
| ASCII | `"Hello, CAW!"` | 11 | 11 | 11 | All three counts agree. |
| Composed acute | `"é"` (`U+00E9`) | 2 | 1 | 1 | One scalar, one grapheme. |
| Decomposed acute | `"e\u0301"` (`U+0065` + `U+0301`) | 3 | 2 | 1 | Same visible letter as the composed form, but 2 scalars. |
| Four-byte emoji | `"😀"` (`U+1F600`) | 4 | 1 | 1 | One scalar, four bytes. |
| ZWJ sequence | `"👩‍🔬"` (`U+1F469` + `U+200D` + `U+1F52C`) | 11 | 3 | 1 | One visible grapheme, three scalars. |
| Flag | `"🇯🇵"` (`U+1F1EF` + `U+1F1F5`) | 8 | 2 | 1 | Two regional indicators, one grapheme. |
| RTL Arabic | `"مرحبا"` (5 letters) | 10 | 5 | 5 | Each letter is 2 bytes; counts agree except bytes. |
| Newline | `"a\nb"` | 3 | 3 | 3 | The newline is counted as one scalar. |
| Long URL | `"https://example.invalid/"` + 60 × `"a"` | 84 | 84 | 84 | ASCII URLs do not diverge; the full URL length counts. |

Reading Table 1: byte length is never the demo limit. A 4-byte emoji
and an 11-byte ZWJ sequence each contribute far fewer scalars than
bytes, while a decomposed letter contributes more scalars than
graphemes.

## Table 2: 419 / 420 / 421 scalar boundary examples

These examples are generated, not pasted. The validation result is
from the current demo validation in `public/model.mjs`
(`countCharacters` plus the 420 limit, with the empty-text check):
419 and 420 scalars pass; 421 scalars fail with `TEXT_TOO_LONG`.

| Example | Generation | UTF-8 bytes | Unicode scalars | Graphemes | Validation |
| --- | --- | --- | --- | --- | --- |
| Mixed, 419 | 418 × `"a"` + `"😀"` | 422 | 419 | 419 | Pass |
| Mixed, 420 | 419 × `"a"` + `"😀"` | 423 | 420 | 420 | Pass |
| Mixed, 421 | 420 × `"a"` + `"😀"` | 424 | 421 | 421 | `TEXT_TOO_LONG` |
| Decomposed, 420 | 210 × `"e\u0301"` | 630 | 420 | 210 | Pass |
| Decomposed, 421 | 210 × `"e\u0301"` + `"e"` | 631 | 421 | 211 | `TEXT_TOO_LONG` |
| ZWJ, 420 | 140 × `"👩‍🔬"` | 1540 | 420 | 140 | Pass |
| ZWJ, 421 | 140 × `"👩‍🔬"` + `"😀"` | 1544 | 421 | 141 | `TEXT_TOO_LONG` |

Two consequences are worth stating plainly, without deciding the
rule in Issue #8:

- A text with only 140 visible graphemes (the ZWJ case) can already
  reach the 420 scalar limit, while a text with 420 visible graphemes
  of plain ASCII also reaches it. Scalar count and grapheme count
  are not interchangeable at the boundary.
- Byte length at the boundary ranges from 423 bytes (mixed ASCII and
  emoji) to 1540 bytes (ZWJ sequences). A byte-based limit would
  accept and reject different texts from the scalar-based limit.

Empty and whitespace-only inputs are a separate check, not a
boundary pass: `""` (0 bytes, 0 scalars, 0 graphemes) and `"   "`
(3 bytes, 3 scalars, 3 graphemes) both fail with `EMPTY_TEXT`
because the demo rejects empty or whitespace-only text before the
length limit matters.

## Verification

From the repository root, with the existing Node runtime and no
added dependency:

```sh
node --input-type=module -e "
import { countCharacters } from './public/model.mjs';
const bytes = (s) => new TextEncoder().encode(s).length;
const graphemes = (s) => [...new Intl.Segmenter('en', { granularity: 'grapheme' }).segment(s)].length;
const show = (label, s) => console.log(label, bytes(s), countCharacters(s), graphemes(s));
show('ASCII', 'Hello, CAW!');
show('composed', 'é');
show('decomposed', 'é');
show('emoji', '😀');
show('zwj', '👩‍🔬');
show('flag', '🇯🇵');
show('rtl', 'مرحبا');
show('newline', 'a\nb');
show('URL', 'https://example.invalid/' + 'a'.repeat(60));
show('mixed-419', 'a'.repeat(418) + '😀');
show('mixed-420', 'a'.repeat(419) + '😀');
show('mixed-421', 'a'.repeat(420) + '😀');
show('decomposed-420', 'é'.repeat(210));
show('zwj-420', '👩‍🔬'.repeat(140));
"
```

Expected output, in order `label bytes scalars graphemes`:

```text
ASCII 11 11 11
composed 2 1 1
decomposed 3 2 1
emoji 4 1 1
zwj 11 3 1
flag 8 2 1
rtl 10 5 5
newline 3 3 3
URL 84 84 84
mixed-419 422 419 419
mixed-420 423 420 420
mixed-421 424 421 421
decomposed-420 630 420 210
zwj-420 1540 420 140
```

The boundary validation results in Table 2 were checked against
the current demo validation: mixed, decomposed, and ZWJ examples
at 419 and 420 scalars apply successfully with the matching
`characterCount`, and at 421 scalars they fail with
`TEXT_TOO_LONG`. No disagreement with the current validation was
found, and no validation code was changed for this guide.

## What this does not establish

- It does not resolve Issue #8. Scalar counting remains provisional
  until that decision is recorded.
- It does not change the existing tests. The existing
  `tests/model.test.mjs` case already covers an emoji-only
  420 / 421 boundary, composed and decomposed accents, unpaired
  surrogates, and an exact ZWJ / RTL text. The new contribution
  here is the human-readable comparison table and the mixed-content
  boundary examples, not a duplicate of that test.
- Grapheme counts are a comparison aid only. They are not proposed
  as the new limit, and they are not checked against the demo
  validation, which counts scalars.
